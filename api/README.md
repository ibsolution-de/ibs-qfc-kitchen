# api — Rust Backend

Single-worker service, built with **axum** + **tokio**, that serves Connect
RPC (protobuf) under `/api` and persists to an embedded **SQLite** database.
It replaces the frontend's earlier localStorage-only prototype: the SPA now
loads its full state over RPC and gets live updates over a server-push
stream (`EventService.Watch`) instead of anything client-local.

## Stack

From `Cargo.toml`:

- **connectrpc** 0.8.1 (`axum`, `server` features) — Connect RPC server, routed via `connectrpc::Router::into_axum_router()`.
- **buffa** 0.8.1 (`json` feature) — the protobuf message/codec runtime this project uses. Note: **buffa, not prost.** Messages implement `buffa::Message` (`encode_to_vec`/`decode_from_slice`), generated by `connectrpc-build` at compile time via `build.rs`.
- **axum** 0.8.9 + **tokio** 1.53.1 (multi-thread runtime) — HTTP server and async runtime.
- **sqlx** 0.9.0 (`sqlite`, `migrate` features) — SQLite pool + migrations, WAL mode.

## Proto packages and RPCs

Eight `qfc.<package>.v1` packages under `proto/qfc/`, each owning one
business case and backed by one `Impl` in `api/src/services/`:

| Package | Business case | Service | RPCs |
|---|---|---|---|
| `session.v1` | current caller's identity | `SessionService` | `GetSession` |
| `events.v1` | live-sync spine | `EventService` | `Watch` (server stream) |
| `team.v1` | employee master data | `TeamService` | `ListEmployees`, `UpsertEmployee`, `DeleteEmployee` |
| `crm.v1` | customers | `CustomerService` | `ListCustomers`, `UpsertCustomer`, `DeleteCustomer` |
| `portfolio.v1` | projects | `ProjectService` | `ListProjects`, `UpsertProject`, `DeleteProject` |
| `strategy.v1` | strategic goals + North Star metrics | `StrategyService` | `ListGoals`, `UpsertGoal`, `DeleteGoal`, `ListNorthStarMetrics`, `UpsertNorthStarMetric`, `DeleteNorthStarMetric` |
| `growth.v1` | 1:1 sessions | `GrowthService` | `ListSessions`, `UpsertSession`, `DeleteSession` |
| `planning.v1` | plan revisions (frozen planning snapshots), assignments, absences, forecast data, holidays | `PlanningService` | `ListVersions`, `GetVersion`, `CreateVersion`, `UpdateVersionMeta`, `DeleteVersion`, `ApplyAssignments`, `ApplyAbsences`, `UpsertQuarterData`, `DeleteQuarterData`, `ListHolidays` |

All eight are registered on the `connectrpc::Router` in `main.rs`.

## Auth

There is no auth logic in this service. The reverse proxy in front of it
(Traefik + oauth2-proxy, see `deploy/argocd/base/ingressroute.yaml`)
terminates TLS and OIDC login and injects `X-Auth-Request-Email` /
`X-Auth-Request-Name` / `X-Auth-Request-Preferred-Username` /
`X-Auth-Request-User` headers; `api/src/auth.rs`'s middleware trusts those
headers unconditionally, upserts a `users` row keyed by email, and hands
handlers a `CurrentUser` via `auth::require(&ctx)`. `/healthz` is exempt (the
container's liveness probe must work before a proxy is reachable).

Environment variables (all read once at startup in `config.rs`):

| Var | Default | Purpose |
|---|---|---|
| `QFC_BIND` | `0.0.0.0:8080` | Address the HTTP server binds to. |
| `QFC_DB_PATH` | `./qfc.db` | SQLite file path (the container image sets `/data/qfc.db`). |
| `QFC_DEV_USER` | unset | Local-dev identity fallback used when no proxy headers are present, format `email\|Display Name`. **Must never be set in production** — it bypasses auth entirely. |
| `QFC_DEFAULT_ROLE` | `pm` | Role assigned the first time a user is ever seen (`employee`\|`pm`\|`bl`\|`sales`, case-insensitive). Never overwrites a role already stored. |
| `QFC_ADMIN_EMAILS` | unset (empty) | Comma-separated emails granted the `admin` role: the accounts are created at startup (`auth::ensure_admins`), before first login; additionally, any matching email is seeded `admin` instead of `QFC_DEFAULT_ROLE` on first sighting. Matched case-insensitively. |
| `QFC_PLAN_REVISION_RETENTION` | `5` | How many plan revisions (frozen planning snapshots) the system keeps, one of `2`/`3`/`5`/`10`. Older revisions are pruned automatically. Only the startup fallback — admins can override it at runtime via `AdminService::UpdateAppSettings` (stored in the `meta` table). The configured retention counts user revisions; the deployment baseline `v1` / `2026` is never pruned. |
| `RUST_LOG` | `info` | Read directly by `tracing-subscriber`'s `EnvFilter`, not by `config.rs`. |

## Access control

Roles are a set per user (`qfc.session.v1.User.roles`), granted and revoked
exclusively by an admin through `AdminService` — a user can never change
their own role set: no self-service RPC exists, and the web app's role
switcher is compile-time dev-only (`import.meta.env.DEV`), so it cannot
exist in a production build. Two server-side guards make an admin lockout
impossible through the API: the `admin` role cannot be removed from the
caller's own account, nor from the last remaining admin (mirrored by the
delete guards).

A role defines which usecases are open. Reads (list/get/watch) are open to
every authenticated user; the mutating RPCs are gated per service — denials
surface as `permission_denied`:

| Service | Mutating RPCs require |
|---|---|
| TeamService (employee master data) | `pm` or `bl` |
| PlanningService (versions, assignments, absences, quarter data) | `pm` or `bl` |
| StrategyService (goals, north star metrics) | `pm` or `bl` |
| GrowthService (1:1 sessions) | `pm` or `bl` |
| PortfolioService (projects) | `pm`, `bl`, or `sales` |
| CustomerService (customers) | `pm`, `bl`, or `sales` |
| AdminService (users, roles, settings, monitoring) | `admin` |

The web app mirrors these gates (hides the controls, routes by role), but
the server is the enforcement point.

Emails are the account identity and behave case-insensitively: every path
that touches `users.email` (proxy headers, `QFC_DEV_USER`, admin
upserts/deletes, `ensure_admins`) normalizes it to trimmed lower-case via
`auth::normalize_email`, so the case-sensitive SQLite primary key never
sees two spellings of one address. Migration
`0004_email_case_normalize.sql` folds any historical rows into that form.

## Storage model

`migrations/0001_init.sql`: low-churn master data is stored as an
id-plus-encoded-protobuf-blob row, so its shape follows the proto message
without a migration per field; high-churn planner rows are typed columns,
since the planner filters/queries them directly.

- Blob tables (`api/src/store.rs`'s `Table` enum): `employee`, `customer`,
  `project`, `strategic_goal`, `north_star`. Each is `(id, updated_at, data)`.
- `one_on_one` is blob-shaped plus an extra `employee_id` column (indexed,
  kept in sync with the encoded payload) — the one exception, hand-written
  in `services/growth.rs` rather than folded into `store::Table`.
- `plan_version`, `assignment`, `absence` are fully typed columns (the
  planner filters on `version_id`/`employee_id`/`project_id`/`date`
  directly). `quarter_data` pairs typed key/position columns with an
  encoded-blob payload for the parts of the message that don't reduce to
  scalars (month arrays, linked project ids, ...).
- `change_log`: append-only audit/event log backing live sync (below).
- `users`: local accounts keyed by email, upserted by the auth middleware.
- `meta`: small key/value store (currently just the seed-completion marker).

## Live-sync contract

`api/src/events.rs`'s ordering invariant, enforced everywhere a service
writes: a `change_log` row is inserted **inside the same transaction** as
the entity write, and the corresponding event is broadcast to live watchers
**only after that transaction commits** — never before, never for a rolled-
back transaction. Every new write path must follow this shape:

```rust,ignore
let mut tx = pool.begin().await?;
store::upsert_blob(&mut tx, store::Table::Employee, &id, &employee).await?;
let mut pending = events::PendingEvents::new();
pending.push(
    events::record(&mut tx, &user.email, EntityKind::Employee, ChangeOp::Upsert, &id, None, Some(employee.encode_to_vec())).await?,
);
tx.commit().await?;
hub.publish_all(pending);
```

`EventService.Watch(since_seq)` subscribes to the live broadcast hub
*before* reading replay rows, then replays every `change_log` row with
`seq > since_seq`, then streams live — so a reconnecting client loses
nothing, and any overlap between replay and live delivery is deduped by
`seq`. `since_seq: 0` means "no replay, start live," not "replay all of
history."

If the requested `since_seq` predates the retention floor (`change_log` is
pruned to the newest ~20k rows, see `events::prune`) or the client lagged
the broadcast channel, `Watch` returns a `DataLoss` error
(`events::reload_required_error`) instead of silently starting mid-history.
The client's only correct response is a full reload of current state,
followed by reconnecting `Watch` with `since_seq` set to whatever it just
observed (see `web/src/api/liveStore.tsx`'s watch loop for the reference
implementation).

## Seeding

`api/seed/seed.json` is the production baseline a fresh database boots
with. It is generated by `pnpm seed:gen` (`tools/gen-seed.ts`) from
`web/src/constants.ts`'s `INTERNAL_CUSTOMER` (IBsolution GmbH, our own
firm, so internal projects always have a client to attach to), converted
through the same `*ToProto` adapters (`web/src/api/adapters.ts`) the
frontend itself uses. The file is embedded into the binary at compile time
(`include_str!`) and loaded by `seed::seed_if_empty` on startup, before the
server accepts connections: if (and only if) the database has never been
seeded, every row is written in one transaction, with no `change_log` rows
produced for any of it.

That is the whole baseline — no employees, no plan versions, no holidays,
no goals. The `MOCK_*` demo dataset still lives in `web/src/constants.ts`
and `web/src/mocks` for tests and local feature development, but it is not
part of the shipped seed. Users are never seeded either: accounts are
created by the auth layer (`QFC_ADMIN_EMAILS` / `QFC_DEFAULT_ROLE`), so a
fresh deployment starts with exactly the configured Admin plus the internal
customer.

Databases seeded by the pre-production demo seed are converged to this
baseline by migration `0003_production_seed_cleanup.sql`, which deletes the
old demo rows (by their seed ids), drops the `seeded` marker, and lets the
minimal seed re-run right after.

## Development

From the repo root:

```
pnpm api:dev     # cargo run --manifest-path api/Cargo.toml
pnpm api:lint    # cargo clippy --manifest-path api/Cargo.toml -- -D warnings
pnpm api:test    # cargo test --manifest-path api/Cargo.toml
pnpm proto:gen   # regenerate the committed TypeScript in web/src/api/gen
pnpm proto:lint  # buf lint proto/
pnpm seed:gen    # regenerate api/seed/seed.json from web/src/constants.ts
```

To run the API and the Vite dev server together locally: Vite's dev server
proxies `/api` to `http://127.0.0.1:8080` (see `web/vite.config.ts`), so
start the API with a dev identity set — the browser has no OIDC proxy in
front of it locally, so without `QFC_DEV_USER` every request is rejected
with 401:

```
QFC_DEV_USER="you@example.com|Your Name" pnpm api:dev
pnpm dev   # separate terminal
```

## Codegen

- **Rust:** `build.rs` runs `connectrpc-build` against every `.proto` file
  under `proto/qfc/` on every `cargo build`, so the generated Rust code is
  never committed. This requires a `protoc` binary on `PATH` (the container
  build installs `protobuf-compiler`; locally, e.g. `brew install
  protobuf`).
- **TypeScript:** `pnpm proto:gen` runs `@bufbuild/buf generate` (via
  `buf.gen.yaml`'s `protoc-gen-es` plugin) and writes the result into
  `web/src/api/gen`, which **is** committed — regenerate and commit it
  whenever a `.proto` file changes.

## Adding a new business case

1. Add messages + a service (or extend an existing one) in
   `proto/qfc/<package>/v1/<package>.proto`.
2. Regenerate both sides: `cargo build` (automatic, via `build.rs`) and
   `pnpm proto:gen` for the TypeScript client.
3. Add a `services::<package>` module implementing the generated service
   trait — reuse `services::crud` if it's a plain blob-backed entity
   (see `services/team.rs`); hand-write it if not (see `services/growth.rs`
   for why `one_on_one` doesn't fit `services::crud`).
4. Register the new service on the `connectrpc::Router` in `main.rs`.
5. Emit `change_log` events for every write, following the pattern above —
   add a new `EntityKind` variant and a `ChangeEvent.body` oneof case in
   `events.proto` if it's a new entity kind, and extend
   `events.rs::decode_body`'s match.
6. On the web side: add `*ToProto`/`*FromProto` adapters
   (`web/src/api/adapters.ts`) and a store method on `LiveStore`
   (`web/src/api/liveStore.tsx`) that calls the new RPC and applies the
   corresponding `ChangeEvent` case in `applyChangeEvent`.
